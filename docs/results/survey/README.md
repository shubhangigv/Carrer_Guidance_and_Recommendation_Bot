# Survey results (real student responses)

The numbers in this folder come from the real Google Form responses. They are generated by scripts;
never type a number here by hand, and always report how many students each number is based on.

## How to run (Windows PowerShell, project root, `.venv` active)

1. Google Form -> **Responses** -> the three dots -> **Download responses (.csv)**.
2. Unzip it and save the file as `data\raw\survey\responses.csv` (create the folder; it is git-ignored, so
   student answers never go to GitHub). Do not edit this file.
3. Run:

```powershell
python experiments\survey_analysis.py   # survey_summary.md + charts: the problem statement (Q1-Q4, Q8, Q9)
python experiments\hit_rate.py          # hit_rate.csv: is the aimed field (Q8) in the top 1 / 3 / 5?
python experiments\ml_compare.py        # ml_compare.csv: ML models vs majority baseline vs the engine
```

Re-run all three whenever more responses arrive; the files are replaced.

## What each file means

| File | Meaning |
|---|---|
| `survey_summary.md`, `*.png` | counts and % per question; the "Key numbers" support the problem statement |
| `hit_rate.csv` | per method (v2 = the app, v2_no_div, v1, random) and k: share of students whose aimed field is among the top-k careers, with a 95% Wilson interval |
| `hit_rate_by_field.csv` | the app's Hit@5 per aimed field (small groups: read with care) |
| `hit_rate_counts.txt` | how many responses were used and why the others were left out |
| `ml_compare.csv` | accuracy and macro-F1 (mean ± std over 5 × repeated stratified k-fold) for each model; `engine_v2` is not trained |
| `ml_confusion_*.png` | which fields get confused with which |
| `ml_feature_importance.csv` | which quiz answers the Random Forest relies on most (explanation only) |
| `ml_counts.txt` | students and fields used; fields left out because they had fewer than 3 students |

## Responses after the analysis cut-off (`later/`)

The survey was closed for analysis at **87 responses** (26 Oct); every file above uses those first 87 rows
(`ANALYSIS_CUTOFF` in `ml/survey.py`; the scripts take `--first-n 0` to use all). 52 more arrived later
(139 on 29 Oct, 47 of them on 28 Oct). `python experiments\later_responses.py` re-runs Hit@k, the ML comparison,
the feature sets and the hybrid on all responses into `later/`, with the same settings and rules (nothing re-tuned),
and splits the engine's hits into "first 87" vs "later" (`batches.csv`, counts in `batches.txt`).
What it shows: the field task grows from 5 to 10 fields, so all numbers drop and are not comparable with the main
ones; on the later responses alone engine v3 Hit@1 is 2.0% (first 87: 14.8%); they lean towards Management,
Business, Law and Life Sciences and have more flat skill answers (15.4% vs 5.7%); the hybrid still beats the
engine and random. The app's field model trains on all responses (more fields it can predict).

## Limitations to write in the report

- XGBoost (`ml_compare.csv`, run 29 Oct once the package was installed): 56.6% accuracy / 0.374 macro-F1. Unlike the
  other three models it ran WITHOUT class balancing (XGBClassifier has no class_weight option), which hurts small fields.
- Engine v2 gives exactly equal top scores to two careers for 7 of the 77 students (5 in different fields). Which one
  comes first depends on how the computer sorts ties, so v2's macro-F1 can differ slightly between PCs
  (0.083 on one, 0.079 on another; accuracy 7.8% on both). Engine v3 and all other numbers are unaffected.

- Q8 is the field a 1st-3rd year student is **aiming for**, not a proven fit or a later job. Agreement with it
  is a sanity check, not "accuracy".
- Small sample from one college; fields with few students give unstable numbers (see the confidence intervals).
- Self-ratings, not tests: students may over- or under-rate themselves.
- The survey fields are mapped to O*NET groups in `config/survey_field_map.csv` (fixed before any result).
- ML models are trained and tested on the same small group with cross-validation; with ~50 students the
  numbers can change a lot when more responses arrive. No hyper-parameter search was done (it would overfit).
